# Интернет-магазин «Web-Larёk»
«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и  отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component
Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`


#### Класс Api
Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter
Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` -  хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные

В приложении используются две сущности предметной области — товар и покупатель, которые описываются следующими интерфейсами.

#### Интерфейс IProduct
Описывает товар, который может быть представлен в каталоге, в корзине или в заказе.

```ts
interface IProduct {
  id: string;
  description: string;
  image: string;
  title: string;
  category: string;
  price: number | null;
}
```

`id` - уникальный идентификатор товара.  
`description` - описание товара.  
`image` - путь к изображению товара (для получения полной ссылки на картинку к нему нужно дописать `CDN_URL`).  
`title` - название товара.  
`category` - категория товара.  
`price` - цена товара в синапсах; `null`, если цена не указана (на витрине такой товар отображается как «Бесценно»).

#### Тип TPayment
Описывает доступные способы оплаты заказа. Пустая строка отдельным значением обозначает, что способ оплаты ещё не выбран, - это позволяет использовать один и тот же тип для поля `payment` как в интерфейсе `IBuyer`, так и в классе `BuyerModel`, не прибегая к приведению типов.

```ts
type TPayment = 'card' | 'cash' | '';
```

#### Интерфейс IBuyer
Описывает данные покупателя, которые указываются при оформлении заказа.

```ts
interface IBuyer {
  payment: TPayment;
  email: string;
  phone: string;
  address: string;
}
```

`payment` - выбранный способ оплаты.  
`email` - email покупателя.  
`phone` - телефон покупателя.  
`address` - адрес доставки.

#### Тип TBuyerErrors
Описывает результат валидации данных покупателя - объект с текстами ошибок по полям `IBuyer`. Вынесен в именованный тип, чтобы не дублировать выражение в местах, где требуется этот тип (методы валидации, обработка ошибок форм).

```ts
type TBuyerErrors = Partial<Record<keyof IBuyer, string>>;
```

## Модели данных

Для хранения и работы с данными в приложении используются три класса-модели. Каждый класс отвечает за свою, не пересекающуюся с другими, часть данных: за получение данных с сервера и за отображение они не отвечают. Ни один из классов не знает о существовании компонентов представления.

Начиная со второго спринта каждая модель принимает в конструктор брокер событий (`IEvents`) и генерирует событие в каждом методе, который изменяет её данные, - так представление и презентер узнают об изменениях, не будучи напрямую связанными с моделью.

#### Класс CatalogModel
Отвечает за хранение каталога товаров: полного списка товаров, полученного с сервера, и товара, выбранного пользователем для подробного просмотра.

Конструктор:  
`constructor(events: IEvents)` - принимает брокер событий, через который будут генерироваться события об изменении данных.

Поля класса:  
`products: IProduct[]` - массив всех товаров каталога.  
`preview: IProduct | null` - товар, выбранный для подробного отображения; `null`, если товар не выбран.  
`events: IEvents` - брокер событий.

Методы класса:  
`setProducts(products: IProduct[]): void` - сохраняет переданный массив товаров в поле `products`, генерирует событие `catalog:changed`.  
`getProducts(): IProduct[]` - возвращает массив товаров каталога.  
`getProduct(id: string): IProduct | undefined` - возвращает товар по переданному id или `undefined`, если товар с таким id отсутствует в каталоге.  
`setPreview(product: IProduct): void` - сохраняет переданный товар в поле `preview`, генерирует событие `preview:changed`.  
`getPreview(): IProduct | null` - возвращает товар, сохранённый для подробного отображения.

#### Класс BasketModel
Отвечает за хранение товаров, которые покупатель выбрал для покупки, и за операции над этим набором товаров.

Конструктор:  
`constructor(events: IEvents)` - принимает брокер событий, через который будут генерироваться события об изменении данных.

Поля класса:  
`items: IProduct[]` - массив товаров, добавленных пользователем в корзину.  
`events: IEvents` - брокер событий.

Методы класса:  
`getItems(): IProduct[]` - возвращает массив товаров, находящихся в корзине.  
`add(product: IProduct): void` - добавляет переданный товар в корзину, генерирует событие `basket:changed`.  
`remove(product: IProduct): void` - удаляет переданный товар из корзины, генерирует событие `basket:changed`.  
`clear(): void` - очищает корзину, удаляя из неё все товары, генерирует событие `basket:changed`.  
`getTotal(): number` - возвращает суммарную стоимость всех товаров, находящихся в корзине.  
`getCount(): number` - возвращает количество товаров, находящихся в корзине.  
`hasProduct(id: string): boolean` - проверяет, находится ли в корзине товар с переданным id.

#### Класс BuyerModel
Отвечает за хранение данных покупателя, которые указываются при оформлении заказа: способ оплаты, адрес доставки, телефон и email, а также за их сохранение, получение, очистку и валидацию.

Конструктор:  
`constructor(events: IEvents)` - принимает брокер событий, через который будут генерироваться события об изменении данных.

Поля класса:  
`payment: TPayment` - выбранный способ оплаты; пустая строка означает, что способ оплаты ещё не выбран.  
`email: string` - email покупателя.  
`phone: string` - телефон покупателя.  
`address: string` - адрес доставки.  
`events: IEvents` - брокер событий.

Методы класса:  
`setData(data: Partial<IBuyer>): void` - сохраняет переданные поля покупателя. Метод принимает как весь объект данных целиком, так и любое отдельное поле - значения полей, отсутствующих в переданном параметре, не изменяются. Генерирует событие `buyer:changed`.  
`getData(): IBuyer` - возвращает все данные покупателя.  
`clear(): void` - очищает данные покупателя, возвращая все поля в исходное (незаполненное) состояние. Генерирует событие `buyer:changed`.  
`validate(): TBuyerErrors` - проверяет валидность полей покупателя (поле валидно, если оно не пустое) и возвращает объект с текстами ошибок. Ключами объекта являются названия невалидных полей, значениями - текст ошибки. Поле, прошедшее валидацию, в возвращаемом объекте отсутствует.

## Слой коммуникации

Помимо данных о товаре и покупателе, приложение оперирует данными, которыми обменивается с сервером. Они описываются следующими интерфейсами (переиспользуют уже описанные `IProduct` и `IBuyer`, а не дублируют их поля).

#### Интерфейс IProductsResponse
Описывает объект, который возвращает сервер на запрос списка товаров.

```ts
interface IProductsResponse {
    total: number;
    items: IProduct[];
}
```

`total` - общее количество товаров.  
`items` - массив товаров.

#### Интерфейс IOrderRequest
Описывает данные, которые отправляются на сервер при оформлении заказа. Расширяет `IBuyer` данными о сумме и составе заказа.

```ts
interface IOrderRequest extends IBuyer {
    total: number;
    items: string[];
}
```

`total` - итоговая сумма заказа.  
`items` - массив идентификаторов товаров, которые входят в заказ.

#### Интерфейс IOrderResult
Описывает объект, которым сервер подтверждает успешное оформление заказа.

```ts
interface IOrderResult {
    id: string;
    total: number;
}
```

`id` - идентификатор созданного заказа.  
`total` - сумма, списанная за заказ.

#### Класс LarekApi
Отвечает за взаимодействие с сервером API «Веб-ларёк»: получение каталога товаров и отправку оформленного заказа. Сам класс не выполняет HTTP-запросы и не хранит состояние приложения - он использует композицию, делегируя выполнение запросов переданному в конструктор объекту, реализующему интерфейс `IApi`. Это позволяет классу оставаться изолированным от конкретной реализации транспортного слоя.

Конструктор:  
`constructor(api: IApi)` - принимает объект, реализующий интерфейс `IApi`, через который будут выполняться запросы к серверу.

Поля класса:  
`api: IApi` - объект для выполнения GET- и POST-запросов к серверу.

Методы класса:  
`getProducts(): Promise<IProductsResponse>` - выполняет GET-запрос на эндпоинт `/product/` и возвращает промис с объектом, содержащим общее количество товаров и их массив.  
`createOrder(order: IOrderRequest): Promise<IOrderResult>` - выполняет POST-запрос на эндпоинт `/order/`, передавая данные заказа, полученные в параметре, и возвращает промис с объектом, подтверждающим оформление заказа на определённую сумму.

## Слой представления

Компоненты представления отвечают только за отображение переданных им данных на странице и за генерацию событий в ответ на действия пользователя. Ни один компонент представления не обращается к моделям данных или к `Api` напрямую - за подготовку данных для компонентов и за реакцию на события отвечает презентер.

Все компоненты наследуются от базового класса `Component`. Три компонента, отвечающие за разные представления карточки товара, имеют общего родителя `Card`, в который вынесен функционал, общий для всех трёх (id, заголовок, цена, брокер событий). Категория и изображение нужны только карточкам каталога и превью, поэтому они вынесены в промежуточный абстрактный класс `ProductCard` - так этот код не дублируется в `CatalogCard` и `PreviewCard`, а `BasketCard`, у которой нет ни категории, ни изображения, наследуется напрямую от `Card`. Иерархия карточек: `Component` -> `Card` -> `ProductCard` -> `CatalogCard`/`PreviewCard`, `Component` -> `Card` -> `BasketCard`. Два компонента форм оформления заказа имеют общего родителя `Form`. Модальное окно (`Modal`) дочерних классов не имеет: всё, что отображается внутри него (карточка товара, корзина, формы, экран успеха), - самостоятельные независимые компоненты, которые презентер вставляет в модальное окно как обычный DOM-элемент.

Для данных, которые компоненты принимают в метод `render`, объявлены новые типы - они не дублируют структуру `IProduct`/`IBuyer`/`IOrderResult`, а собраны из них с помощью `Pick` и пересечения типов.

```ts
type TCardBase = Pick<IProduct, 'id' | 'title' | 'price'>;

type TCatalogCard = TCardBase & Pick<IProduct, 'category' | 'image'>;

type TPreviewCard = TCatalogCard & Pick<IProduct, 'description'> & {
    buttonText: string;
    buttonDisabled: boolean;
};

type TBasketCard = TCardBase & {
    index: number;
};

interface IGalleryRender {
    items: HTMLElement[];
}

interface IHeaderRender {
    counter: number;
}

interface IBasketRender {
    items: HTMLElement[];
    total: number;
    valid: boolean;
}

interface IModalRender {
    content: HTMLElement;
}

interface IFormState {
    valid: boolean;
    errors: string;
}

type TOrderFormRender = Pick<IBuyer, 'payment' | 'address'> & IFormState;

type TContactsFormRender = Pick<IBuyer, 'email' | 'phone'> & IFormState;

type TSuccessRender = Pick<IOrderResult, 'total'>;
```

#### Класс Modal
Отвечает за открытие, закрытие модального окна и за отображение в нём произвольного переданного содержимого. Не имеет дочерних классов.

Конструктор:  
`constructor(container: HTMLElement, events: IEvents)` - принимает корневой DOM-элемент модального окна (`.modal`) и брокер событий.

Поля класса:  
`events: IEvents` - брокер событий.  
`closeButton: HTMLButtonElement` - кнопка закрытия (`.modal__close`).  
`contentElement: HTMLElement` - контейнер содержимого модального окна (`.modal__content`).

Методы класса:  
`set content(value: HTMLElement)` - заменяет содержимое `.modal__content` переданным элементом.  
`open(): void` - добавляет модификатор `modal_active`, делая модальное окно видимым.  
`close(): void` - убирает модификатор `modal_active`.

События: клик по `.modal__close` или клик за пределами `.modal__container` (по оверлею) генерирует `modal:close`.

#### Класс Gallery
Отвечает за отображение списка карточек товаров на главной странице.

Конструктор:  
`constructor(container: HTMLElement)` - принимает элемент `<main class="gallery">`.

Методы класса:  
`set items(value: HTMLElement[])` - заменяет содержимое каталога переданными элементами карточек.

#### Класс Header
Отвечает за кнопку открытия корзины и счётчик количества товаров в ней.

Конструктор:  
`constructor(container: HTMLElement, events: IEvents)` - принимает элемент `.header` и брокер событий.

Поля класса:  
`events: IEvents` - брокер событий.  
`basketButton: HTMLButtonElement` - кнопка корзины (`.header__basket`).  
`counterElement: HTMLElement` - счётчик товаров (`.header__basket-counter`).

Методы класса:  
`set counter(value: number)` - обновляет текст счётчика.

События: клик по `.header__basket` генерирует `basket:open`.

#### Класс Card (абстрактный)
Общий родитель для трёх представлений карточки товара. Хранит логику, одинаковую для всех трёх: id товара, отображение заголовка и цены, брокер событий.

Конструктор:  
`protected constructor(container: HTMLElement, events: IEvents)` - принимает корневой DOM-элемент карточки и брокер событий.

Поля класса:  
`id: string` - id отображаемого товара; используется наследниками при генерации событий.

## Презентер

За логику приложения отвечает единственная страница, поэтому презентер не вынесен в отдельный класс - он реализован как набор обработчиков событий в основном скрипте приложения `main.ts`. Такой выбор сделан из соображений соразмерности задачи: у приложения один слой данных, один слой представления и одна страница, поэтому дополнительный класс-обёртка не добавил бы разделения ответственности, а лишь усложнил бы код. Инверсия зависимостей соблюдена и без выделения презентера в класс: все компоненты (модели, `LarekApi`, компоненты представления) не зависят друг от друга напрямую и получают свои зависимости (брокер событий, `IApi`) через конструктор.

В `main.ts` создаются единственные экземпляры моделей данных, `LarekApi` и постоянных компонентов представления (`Modal`, `Gallery`, `Header`, `Basket`, `OrderForm`, `ContactsForm`, `Success`, `PreviewCard`) - они переиспользуются между рендерами. Карточки каталога и корзины (`CatalogCard`, `BasketCard`) создаются заново на каждый рендер списка, так как их количество меняется.

Презентер только подписывается на события (`events.on(...)`) и не генерирует ни одного события самостоятельно - генерация событий происходит исключительно в моделях данных и в компонентах представления. Обработчики делятся на две группы:

- обработчики событий моделей данных (`catalog:changed`, `preview:changed`, `basket:changed`, `buyer:changed`) - берут актуальные данные из моделей через их методы, строят из них компоненты представления и вызывают их `render`. Это единственное место, где происходит перерисовка представления по причине изменения данных;
- обработчики событий представления (`card:select`, `card:buy`, `basket:remove`, `basket:open`, `order:open`, `order:change`, `order:submit`, `contacts:change`, `contacts:submit`, `modal:close`) - вызывают методы моделей данных или открывают/закрывают модальное окно. Открытие модального окна - второй случай, помимо изменения данных, когда презентер напрямую обращается к представлению. Именно поэтому при открытии каждой из форм оформления заказа презентер сбрасывает текст ошибок: при первом показе форма, как на макете, без сообщений об ошибках - они появляются после первого изменения данных.

Названия всех событий приложения объявлены в одном месте - константе `AppEvent` (`src/utils/constants.ts`) и используются и моделями, и компонентами представления, и презентером. Тексты интерфейса (`ButtonText`, `PRICE_UNIT` и др.) и динамические CSS-классы (`CssClass`) также вынесены в `constants.ts`, а повторяющаяся логика форматирования (`formatPrice`, `joinErrors`) - в `src/utils/utils.ts`.

Чтобы получить данные, которые нужны компоненту представления, но хранятся в разных моделях (например, при открытии превью товара нужен и товар из `CatalogModel`, и информация о том, есть ли он в `BasketModel`), презентер запрашивает их у каждой модели по отдельности через уже существующие методы и объединяет в единый объект прямо в обработчике события - сами модели друг о друге не знают.
